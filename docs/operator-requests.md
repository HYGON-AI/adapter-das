# 算子需求提报标准（operator-requests）

> 本文回答：**怎么向算子组/供应商提一条能用、能验收、不返工的算子需求。**
> 核心原则一：**需求锚定开源 sglang 的算子契约面，不锚定任何 HCU 侧实现**。
> 提报方不指定算子落在哪个库（aiter / lightop / 自研 wheel）——那由垫片层
> 的路由与 catalog 裁决；提报方只保证契约本身清晰、可验证、带证据。
> 核心原则二：**需求文档是机器数据的治理过滤产物**，不是聊天记录——
> 原始数据（缺口、频次、性能账）从注册表/catalog/门禁导出，成文前过
> §2 判据。
>
> 配套：治理边界 [governance.md](governance.md)、后端目录
> `hcu_adapter/hcu_config.py`（BACKEND_CATALOG）、运行时注册表
> `hcu_adapter/registry.py`（`HCU_ADAPTER_DUMP`）。

## 0. 一条需求的最小合格线（缺一不予受理）

1. **契约签名**：函数名、参数名、形状/dtype、返回值、默认值——**逐字抄
   上游源码并注 commit 锚**，禁止口头转述或凭记忆写。上游 DSL 系（如 fa3
   的 kwargs 包装、deep_ep 的位置参）必须注明"上游调用点是怎么展开的"。
2. **版本锚**：`contract @ sglang v0.5.21 (commit 8097063)`。移动靶必须钉
   死——上游换版时按 §4 增量更新，不发全量重提。
3. **语义说明**：量化 scale 语义（per-channel/per-token/block 的 axis）、
   causal/window 对齐方向（bottom-right？）、布局（HND/pages/页粒度）、
   累加精度（fp32 accumulate？）、图捕获契约（capture-safe？静态形状？）。
   参照实现 = 上游 CUDA/AMD 分支源码，不是我们的 shim。
4. **现状账**：HCU 今天怎么活下来的（emu / 回退 / 响亮 stub / 缺失），
   以及代价（慢多少倍、挡住哪些模型/特性）。没有现状账不算缺口证据。
5. **频次与影响面**：生产栈上每次请求都会撞到，还是特定模型/特性才走；
   挡住了路线图上的哪个节点（模型行 / MTP / PD / EP）。
6. **验收判据（Acceptance）**：可执行的判绿标准。数值域给容差和参照
   （如"vs 上游 CUDA 输出，bf16 cos ≥ 0.999 / fp32 rel ≤ 1e-3"）；行为域
   给锚点（如"e2e N 锚点 + 并发零串扰 + graph replay 后输出一致"）。

## 1. 需求来源：机器数据先行，人只做过滤

提报前先拉三类机器数据，人工成文只是给它们加"影响面"和"优先级"：

| 数据 | 出处 | 用法 |
|---|---|---|
| 缺口清单 | `HCU_ADAPTER_DUMP` 的响亮 stub 项 + catalog `planned` 后端 | 需求主干的候选池 |
| 现状路径账 | registry `log_summary` 启动行 + catalog note（emu/回退标记） | §0.4 现状账的事实来源 |
| 性能对照 | 门禁/探针已有格点（如 `_bench_*`、fused-MoE 单测 TF/s） | §0.5 代价量化 |

频次数据不够时（还无生产栈运行），允许以"路线图阻塞"替代频次作为
优先级论据，但必须注明证据等级。

## 2. 提报前的治理过滤（shim ≠ spec）

垫片层记录的是**我们怎么绕**，不是**接口应该长什么样**。成文前把候选
需求过两道闸：

1. **方向闸**（对照 governance 判别问句）：上游 AMD/CUDA **有**该行为 →
   需求按"对齐参照语义"表述，验收以参照实现为金标；上游**没有** → 这是
   私有能力需求（governance §0/plugin 轨迹），明确标注"契约为我方建议
   形状，上游无义务对齐"，不得写成"补齐缺口"。
2. **妥协清洗**：垫片实现里的一方妥协（alias 别名、kwarg 补位、参数
   重排、预打包 hook 等）**禁止进入契约列**。它们只能出现在现状账里，
   作为"若接口原生按 [建议形状] 提供，这些适配可整体消失"的论据。
   反向表述亦须守：验收判据不得包含任何我方 shim 当前行为。

## 3. 文档结构（每条需求一节，一个文档一个版本锚）

```markdown
## <算子名>（<上游符号 path>）
- 契约     : 签名 + 形状/dtype（逐字抄上游，@ <版本锚>）
- 语义     : scale/布局/对齐/精度/图捕获契约
- 现状     : emu? 回退? stub? 代价（x 倍 / 挡住 <模型或特性>）
- 优先级   : <P0-P3> + 论据（频次 或 路线图阻塞 + 证据等级）
- 验收     : 数值域（参照+容差）/ 行为域（e2e 锚点清单）
- 建议形状 : （可选）若上游形状不理想，给出我方建议与理由
```

配套物（随文档一并交付）：最小复现/验收脚本（按 tests/tools 命名规约
`_probe_*` / `_test_*`）；若已有一档可用实现（如 triton ref），附其对拍
结果作为"金标可达"的证明。

## 4. 版本漂移与闭环

- **锚更新**：追上游 release 时，L0/L1 过一遍后按新版本出**增量 diff**
  （新增符号、签名变化、语义变化），不重发全量；被上游删除/改签的旧条
  目标注"@旧锚 作废/适用范围"。
- **闭环回执**：算子侧交付后走既有验收链（ref 数值测试 → catalog
  `candidate` → e2e → 转正，governance §5/§3）；验收结论回写本需求条目，
  catalog 状态随迁。**需求文档随交付迭代，不是一次性交付物。**
- **利益反向流**：我方已验证可用的实现（如 aiter fla 家族、CK GDN）同样
  按 §0 格式反向提报给算子组（角色="我方已有，建议采纳/对齐"），一条
  标准双向适用。

## 5. 反模式

- 口头转述签名（"就是个 attention，你看着办"）——必须逐字抄上游。
- 把 shim 的私有妥协写进契约（"你们就按 (input, output, mask_m,
  expect_m) 这个顺序"——那是 lightop 的凑法，不是契约）。
- 无现状账直接要"新算子"——数据库只有一行"快"没有基线，无法排优先级。
- 验收只写"能跑"——可执行判据是需求的组成部分，不是验收阶段再补的事。
- 需求混政治：属于 plugin/上游 push 轨迹的能力（governance §5.1）不要
  以"adapter 缺口"名义提报，两类需求分文档分轨道。
